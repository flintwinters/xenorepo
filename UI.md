# Interface direction

Create a self-contained, full-viewport application in a Gruvbox Dark, late-Windows-98 industrial control-panel aesthetic. Treat those names as implementation anchors: use the familiar warm Gruvbox family and the compact, square, visibly layered component language of serious late-1990s desktop operations software. It is neither a modern card dashboard nor a decorative terminal.

Build one outer instrument frame: a very shallow utility rail across the top, a very shallow mode and status rail across the bottom, and a tightly fitted mosaic of work panes occupying everything between. The top rail is operational chrome, not a prominent site-navigation header. Let a small identity mark, terse context, live summary, and a few compact commands share one line. Pane edges must align into a strong two-dimensional grid with only hairline seams between them. Use an asymmetric composition led by one dominant workspace and one broad ledger or stream; subordinate regions should remain visibly narrower or shallower.

Use the canonical Gruvbox Dark relationship of warm charcoal backgrounds, cream foreground text, muted secondary text, and the recognizable bright red, green, yellow, blue, purple, aqua, and orange accents. Pane bodies belong to one quiet family of dark neutral surfaces. Apply restrained Windows 98 skeuomorphism vertically rather than using the pale raised borders of the stock operating system: fine upper-edge highlights, gentle top-to-bottom shading, narrow cast shadows directly below title strips and controls, and recessed tracks or plotting fields. Keep corners almost square. Nothing should appear to float far above the interface.

Cap every primary pane with the same slim title-strip construction. Give different panes distinct muted instrument hues so regions can be located instantly, while reserving the quietest colors for less important panes. Each strip has dark high-contrast text, a brighter upper rim, a deeper lower rim, and a short shadow underneath. Begin each title with a compact dark index plaque. Saturated color belongs chiefly to these strips and to small semantic signals, never to large pane bodies.

Use tiny, crisp monospaced typography throughout. Compactness should come from shallow chrome, near-solid rows, strict column alignment, clipping, and fine separators—not from illegibility. Use bold weight selectively for titles, states, and key values. Every visible datum or control must plausibly help operate this particular product; do not manufacture density with ornamental labels or repeated summaries.

All commands use the same Gruvbox-dark Windows 98 push-button construction: compact square dark faces, crisp outlines, a faint top highlight, and a short lower shadow. Keep individual actions restrained and similar in size. Tabs resemble compact late-1990s property-sheet tabs translated into Gruvbox Dark: contiguous flat segments in a shallow tab well, with selection marked by accent color and a darker ledge. Never use pills, translucent glass, rounded modern cards, isolated soft shadows, oversized buttons, colored button faces, animation, or transitions.

Preserve classic Windows 98 push-button mechanics: at rest the key has a faint inner highlight above, a darker inner edge below, and a compact cast shadow beneath the face. While pressed, the cast shadow visibly collapses and the darker inset shadow strengthens, making the face appear mechanically depressed rather than merely changing color. Restore the resting shadow on release. Keep this response instantaneous with no transition or animation. Do not reinterpret individual commands as primary, destructive, or selected variants; state belongs beside a command, not in a differently styled key.

Tabs inherit the type scale but discard the push-button bevel and pressed behavior. Follow the late-1990s property-sheet model while keeping the faces flat: transparent contiguous tabs divided by crisp rules, with the active tab visually joining the content plane. The selected tab's colored upper marker and shallow dark fill cast a compact shadow directly below the entire tab, forming a small lower shelf over the content beneath it. Unselected tabs cast no such shadow.

Render charts directly on ruled dark plotting fields with simple luminous marks and restrained vertical shading. Render tables and event streams as rigorous ledgers with aligned columns, thin cell rules, clipped overflow, and sticky headings where useful. Render meters as narrow recessed tracks with bright fills. Use small consistent signal colors for selected, nominal, caution, critical, and secondary states.

Make responsive behavior a change in information topology, not a scaled miniature. At broad widths, show a narrow index or navigation pane, the dominant work pane, a narrow contextual inspector, and a broad lower ledger when those regions fit the product. At a middle width, remove the contextual inspector first and let the dominant and lower regions absorb its space while the index remains. At a narrow width, remove the index too, simplify the utility and status rails, and hide low-priority table columns. Preserve a useful vertical pairing of the dominant work area above its ledger or secondary workspace. Horizontal clipping of incidental chrome is preferable to shrinking the entire UI into unreadability, but primary content must remain operable. The document stays fixed to the viewport; only data-heavy pane bodies scroll.

Use semantic landmarks, visible keyboard focus, and real compact interactions. Keep the markup flat: a wrapper must contribute layout, scrolling, clipping, positioning, or unique styling to justify its existence. Deliver a single HTML document with embedded CSS and JavaScript and no external dependencies.

Always ask "is this UI element providing something useful to the user in its current form?" - if not, remove it.

All interactions should have an immediate visual confirmation.  There should be no hidden UI state, a second user should be able to myopically visit a page and pick up exactly where another user left off at any point in time.
